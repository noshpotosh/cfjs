cf-data

Load one JSON response or global value and render it once into a retained cf-data element. 

<cf-data src="./data/examples/projects.json" name="response">
        <template><h2 cf-text="response.title"></h2></template>
      </cf-data>

Attributes

src

URL · required alternative
An HTTP(S) JSON URL relative to document.baseURI. Supply exactly one non-empty src or source; neither has a default. Successful and in-flight JSON requests are shared by resolved absolute URL for the document lifetime. A request times out after 10 seconds; failed requests are evicted.

source

Property path · required alternative
An own-property path on window only, such as projectData or app.projects. Dotted segments follow the binding path rules. Undefined is an unknown-source error; null, false, and 0 are valid values. A function is called without arguments or a receiver; its result, or a promise value, is awaited. Providers handle their own timeouts and caching. Sources must exist when lookup begins; there is no retry or wait for later definitions.

name

Identifier · required
The response alias. Use a JavaScript-style identifier: letters, underscore or dollar sign initially, then letters, digits, underscore or dollar sign. There is no default. This alias is the only initial binding in the template context.

Child templates and scope

The first direct template without a data-state attribute supplies the result. It is required. The first direct template with each supported state supplies optional fallback markup. Templates themselves are consumed when the element replaces its children.

loading

data-state value · optional
Cloned immediately while the element loads, replacing its children. Static markup; bindings are not evaluated.

error

data-state value · optional
Cloned after source, request, JSON parsing, or rendering failure. Static markup with no error binding context. Without it, CFJS creates <p role="alert">Content could not load.</p>.

Bindings and loops run inside the result template. Includes inherit that context. A nested cf-data starts independently after its parent mounts. Its source reads only window, never an enclosing data or loop alias. Its result template starts with only its own name alias.

Resulting DOM and timing

The cf-data wrapper stays; successful output replaces all its children. Lookup starts in a microtask after connection. Inline classic scripts activated by the same include run first, but asynchronous scripts and modules may still be pending. Rendering is one-time, including after removal and reconnection. Attribute changes do not trigger rendering.

aria-busy="true" is set while loading and removed afterward. Disconnected elements ignore late success and failure output; requests continue. See Events and lifecycle.

Empty results, failures, and retry

There is no data-level empty state: use a loop empty template for an empty array. A valid null response can produce blank bindings. Failure sets data-cf-error and emits a bubbling cf:error with detail.error. No automatic retry occurs. Create a new element to retry; a failed JSON request can then be requested again.

Follow Render JSON and global data for a complete task.

Use cf-if to choose a branch once in the current data or loop context. Only the selected template is rendered; nested data resolves its source on window and gives its result a separate scope. Loading, error, and loop empty templates remain static.

Independent global sources

Use a nested global source for optional details. A zero-argument global function starts when the nested element connects, so the parent can appear before optional requests finish. Each nested element owns its loading/error templates and events. Parent readiness does not imply nested completion. Row-specific values must be prepared in the parent and rendered with bindings, loops, or conditions; nested source paths cannot interpolate row IDs.
