Performance

CFJS is small, but content fetched after JavaScript starts can still delay the first useful view. Measure the actual page before tuning it.

Show critical content early

Keep the primary heading and hero in initial HTML. Use an ordinary image src, width and height, and fetchpriority="high" for the one critical image. Do not lazy-load the hero; reserve lazy loading for offscreen images. Load CFJS with defer and put essential layout CSS in the document stylesheet.

The example reserves space in a persistent section outside the replaced include. Loading content and final content should have similar dimensions. This reduces layout movement without hiding the page.

Keep critical content outside include trees

Progressive mounting is not supported. Put critical content in initial HTML or use separate live includes. Nested branches wait for complete preparation before mounting.

Keep optional data independent

Return basic list data before optional work. Use a nested global source="optionalDetails" with a loading template. Nested sources cannot read row aliases. For row-specific details, prepare them in the parent source or use application code. Keep loading and result dimensions similar.

Serve browser-native source

There is no CFJS compiler or server renderer. Serve authored pages and fragments directly, and measure the browser requests and rendering costs. Keep essential content in the entry document.

Keep critical include trees shallow

Nested branches prepare sequentially, and nested URLs are discovered after their parents arrive. Separate live includes start independently. A whole include tree mounts atomically: a slow nested footer can delay critical content in the same tree. Keep critical content outside that tree or in an independent branch.

HTML and JSON requests are deduplicated within the page. Configure compression and appropriate HTTP caching on your host; in-memory request caching does not replace those server settings.

Large data renders and responsiveness

Preparation happens off-document. Loading content stays visible until the complete result mounts, and scripts activate in document order. CFJS does not yield to the browser during preparation: once its requests have arrived, a render's cloning, binding, mounting and script activation run without CFJS-initiated pauses, so very large renders can produce long tasks.

Keep large lists bounded in your application. There is no pagination or virtualization API in CFJS.

Fragment request caching

Each successful HTML request keeps response text for the document lifetime. Every include parses that text afresh before applying slots, nested includes and bindings. DOM is never shared. Scripts activate per instance; styles retain deduplication and order. Redirect aliases use separate requested-URL keys. Failed requests are evicted; validation failures retain cached response text. There is no cache invalidation API.

Measure your page

Use your browser's network and performance tools to inspect the actual page. Compare cold and warm loads, keep the browser and machine consistent, and look for delayed critical content, layout shifts, and long main-thread tasks. Results from one local page are not performance guarantees.

Keep critical content in the entry HTML, use independent includes where appropriate, and bound large lists. The v0.1 repository keeps runnable examples and behavioral browser tests; the older benchmark runners and historical reports have been removed.

Inspect browser traces

Record a load or interaction in browser developer tools to inspect request timing, scripting, layout, and paint. Profiling adds overhead, so confirm improvements with ordinary page loads too. CFJS has no production tracing API.
